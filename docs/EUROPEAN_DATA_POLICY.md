# European processing and no-training policy — 12 October 2026

Markus requested a separate PR to enforce European invoice-content processing and exclude images/text/results from provider model training. This implementation is independent of the iOS work. It makes no inference calls, changes no supplier account settings, and does not modify the running service, private provider config, admin selection, original ledger or phone state. Deploying the changed backend without new reviewed configuration will block the current global profiles. Do not silently change a saved selection or widen a budget to restore availability.

## Mandatory behavior

`europe-no-training@1` has no production opt-out or environment switch. Europe means **EEA + Switzerland**, consistent with the reviewed OpenAI/Mistral regional boundaries; it is not a promise of EU member-state-only processing. This applies to invoice content (images, OCR text, layout and generated results), not a blanket regional guarantee for account/billing/support metadata. Local rules and synthetic fixtures remain available, but a synthetic definition cannot dispatch external content.

Every external profile needs both a supported European endpoint and dated operator-reviewed evidence for the exact account alias, endpoint, model, operation and outbound payload classes. `no_training` must be verified true. The OpenAI image route additionally requires `image_processing_approved=true`, after confirming the provider's enhanced retention-control approval and applicable agreement. Approval dates are checked in UTC, inclusive of the expiry date; future, expired, missing and mismatched approvals fail closed. Evidence references identify private account checks/agreements; the backend does not execute or fetch them.

Checks run in the profile catalogue/selection, atomic acceptance before budget reservation, worker before adapter invocation, and immediately before external dispatch. The extended adapter also checks its immutable option snapshot and each actual URL, including polling. Hybrid OCR and LLM stages are checked independently; text/layout need their own approval coverage. A regional outage, redirect or unsupported model does not trigger a global endpoint, alternative provider or retry. Policy errors use `data_policy_blocked`; availability reasons are visible in the existing authenticated profile response. Expiry after startup updates availability on the next profile read.

An existing idempotency key retrieves its original stored result even if its profile is now blocked; it never dispatches again. Recovered jobs remain interrupted rather than replayed. Policy-blocked jobs release only undispatched holds; dispatched rows and their holds remain intact. Approval changes produce a new profile version. Adding an absent approval does not alter legacy configuration serialization/hashes; old evidence is not relabelled as European or compliant.

The current direct Gemini/AI Studio, Anthropic, Together, xAI, AWS Textract, Azure Document Intelligence and Mindee routes are blocked by this policy. A Frankfurt AWS hostname alone is insufficient evidence for all content-use controls. This PR does not add Vertex AI, Azure OpenAI or Bedrock adapters or infer that an unsupported provider lacks European offerings. A later reviewed route can be added explicitly with transport and policy tests. Mistral model/feature support must be checked per operation; a regional hostname does not by itself establish that OCR/annotations are available for the exact model.

## Activation

1. Obtain and privately retain the supplier's applicable processing/no-training terms and account-specific approvals. For OpenAI, verify enhanced image eligibility and the retention amendment; API no-training by default alone is insufficient for European image processing.
2. Recheck exact model/operation support through read-only provider catalogues and account settings. Confirm training/data-sharing controls are disabled in the specific organization/project. This PR does not perform those account checks or assert they are currently satisfied.
3. Create a **new** operator profile in ignored `.local/providers.json`, using `providers.europe.example.json` as a disabled starting point. Preserve existing profiles, prior private configs, saved selection, budget plan and frozen job snapshots. Recheck regional tariffs and ceilings first: Mistral documents a 10% regional token surcharge; do not treat global tariffs or legacy reservation ceilings as regional pricing evidence. No additional call allowance is granted.
4. Add `data_approval` only after verification. It requires `account_alias`, `endpoint_host`, `model`, `operation`, `payload_classes`, `processing_boundary: "eea_switzerland"`, `no_training`, `image_processing_approved`, `checked_at`, `expires_at`, `region_evidence`, `training_evidence` and `retention_note`. Set `verified_processing_region` on the provider config to `eea_switzerland`. Use actual review/expiry dates and private evidence references. Include `image` for direct processing and `ocr_text` plus `layout` for a hybrid interpreter. Evidence references must not contain credentials or invoice values.
5. After review, plan an idle service deployment; do not restart active jobs or run a second owner. Select the new version explicitly in admin. New profile versions need their normal mobile validation. Inference verification requires separately authorized bounded calls; no invoice upload was made for this PR.

No-training controls are contractual/account controls, not a prompt instruction or a universal request flag. A dated approval is an operator attestation, not independent hardware attestation. Re-review on changes to keys/accounts, terms, region, models or relevant features, and revoke local approvals immediately if vendor controls change. Current account state is not polled automatically. Regional processing does not by itself verify retained-content location or access. Provider retention, safety review exceptions, support access, subprocessors and transfers of operational metadata remain separate legal checks. `store=false` does not mean zero retention. Do not promise zero retention or GDPR compliance from this gate alone. Historic opt-outs cannot be assumed to erase previously retained data or training already performed.

## Sources checked on 12 October 2026

- [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data): API data is excluded from training unless sharing is explicitly enabled; European processing requires the applicable eligibility/retention controls and images require enhanced approval. System data is outside the content-residency guarantee.
- [Mistral regional inference](https://docs.mistral.ai/inference/regional-inference): global endpoint has no location commitment; EU endpoint geography includes EU/EFTA; model/features vary and token pricing has a regional surcharge.
- [Mistral training controls](https://help.mistral.ai/en/articles/347617-do-you-use-my-user-data-to-train-your-artificial-intelligence-models) and [zero retention](https://docs.mistral.ai/admin/monitor-comply/zero-data-retention): training opt-out and retention are distinct controls.
- [Google Document AI security](https://docs.cloud.google.com/document-ai/docs/security): Cloud content-use/security controls, separate from the Gemini Developer API integration.
